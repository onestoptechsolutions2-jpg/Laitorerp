## Backlog

### 1. [partially fixed 2026-08-22] Calendar "New Event" and Leads "Create" don't save — Save re-opens the panel stack instead of submitting
**Symptom:** Calendar → New Event → Save does nothing but flash the parent overlay menu. CRM → Leads → New Lead → Save does the same thing instead of persisting the record.
**Files:** `Leitor.Erp/Pages/Calendar/Create.cshtml.cs`, `Leitor.Erp/wwwroot/leitor-layout.js`, `Leitor.Erp/Pages/Shared/Components/FormOverlay/Default.cshtml`.
**Investigation:** the original "submit-button selector collision" hypothesis didn't hold up — `initFormOverlay()`'s `bindFormSubmit()` in `leitor-layout.js` is correctly wired (real `<form>`, real `fetch()` POST with the XHR header, real JSON-redirect handling), and both `Calendar/Create.cshtml.cs` and `Leads/Create.cshtml.cs`'s `OnPostAsync` correctly branch on `OverlayRequest.Is(Request)`. Two real bugs found by tracing it end to end instead:
- **a. [x] fixed** — Calendar's `EventInput.StartDate` is `[Required]` but only gets pre-filled when opened via FullCalendar's `dateClick` (which appends `?StartDate=...`); the plain "+ New Calendar Event" header button links here with no query string, so the date picker renders blank. A user who doesn't notice they need to pick a date gets a silent `[Required]` validation failure — the overlay redisplays the same-looking form with no obvious change, indistinguishable from "clicking Save does nothing". Fixed by defaulting `EventInput.StartDate = DateTime.Now` at declaration (same pattern already used by `FieldService/Jobs/Create.cshtml.cs` and `Support/WarrantyClaims/Create.cshtml.cs`), so `OnGetAsync`'s existing query-string override still takes priority when present.
- **b. [x] fixed** — real bug in `leitor-layout.js` shared by *every* overlay Create/Edit form (not just Calendar/Leads): the POST-response handler only branched on JSON vs. not; any non-OK, non-JSON response (an antiforgery-validation 400, an unhandled 500) had its raw HTML error page piped straight into `renderFragment()`, silently replacing the user's in-progress form with that error page's markup. `bindFormSubmit()` then finds no `<form>` in it and gives up quietly — no visible error, no way to retry, exactly matching "clicking Save does nothing". Fixed: non-OK responses now show `L["SomethingWentWrong"]` via `abp.message.error` (new `data-error-text` attribute on `#leitor-overlay-modal`, same pattern as the existing `data-loading-text`) and re-enable the Save button, instead of touching the modal body. A 200-OK validation redisplay (Razor Pages returns 200 even when `ModelState.IsValid` is false) is unaffected and still goes through `renderFragment()` as before.
- **Leads/Create** has no equivalent required-field trap (`Name` is a visible required text box, not a silently-blank date picker) — its reported failure is most plausibly explained by fix (b) alone, since it shares the exact same `leitor-layout.js` submit path.
**Still needed:** neither fix has been verified in a live browser — local Postgres auth is still the blocker per `feature_overlay_modal_ui_2026-08-11`. `dotnet build` on `Leitor.Erp.csproj` passes clean with these changes (0 errors, only pre-existing unrelated warnings). No automated test added: (a) is a one-line default-value change with no meaningful C# behavior to unit-test, and (b) is client-side JS with no test harness in this repo — `Leitor.Erp.Tests` has no HTTP-pipeline/Razor-Page-level tests at all yet (everything is AppService-level), so a real regression test for either fix would mean building new antiforgery-aware TestServer test infrastructure, not extending an existing pattern. Flagging that gap rather than faking coverage.

### 3. [partially fixed 2026-08-22] Quotes Detail breaks the overlay pattern, action buttons should collapse into one menu; Confirm dialog bug (c) is fixed
**Files:** `Leitor.Erp/Pages/Sales/Quotes/Detail.cshtml(.cs)`, `Leitor.Erp/wwwroot/leitor-notify.js`.
Three sub-issues on one page:
- **a. [ ] open** The page renders as a plain full page instead of inside the overlay stack used elsewhere (Customers/Leads/Vendors).
- **b. [ ] open** The action row (Edit / Convert to Order / Download PDF / Email to Customer / Share via WhatsApp / Back to list) should collapse into a single "Actions" button that reveals a dropdown — the reporter wants this pattern applied everywhere a similar action row exists (Orders, Invoices, Purchase Orders detail pages all have the same shape — see their `Detail.cshtml.cs` files).
- **c. [x] fixed** Clicking **Confirm** on the "Convert to Order?" dialog does nothing. **Root cause found and fixed**: this wasn't specific to Quotes at all — every `data-confirm` form in the app (`wwwroot/leitor-notify.js`'s `initConfirmForms()`) re-submitted via `form.requestSubmit()` after confirmation, which re-dispatches a real `submit` event through the *entire* listener chain a second time, including a buggy LeptonXLite theme jQuery handler. Confirming just fed the theme's broken handler the exact sequence that hangs it, silently. Switched to classic `form.submit()`, which bypasses the DOM event system entirely (spec: no `submit` event fires), so nothing can intercept it. This also fixed the user-reported "Leads Convert to Customer does nothing after Confirm" bug — same shared mechanism, confirmed via code trace (not directly reproduced live, since local Postgres auth is still broken per `feature_overlay_modal_ui_2026-08-11`). Verify live on both Quotes→Convert to Order and Leads→Convert to Customer next deploy.
**Fix still needed for a/b:** extend the Customers/Leads/Vendors overlay mechanism to Quotes Detail; build one shared actions-menu partial (candidate: `Pages/Shared/_ActionsMenu.cshtml`) and adopt it on Quotes/Orders/Invoices/Purchase Orders detail pages instead of duplicating a button row on each.

### 5. [diagnosed 2026-08-22, not fixed] Categories index shows "No results found" despite Catalog having categories
**Files:** `Leitor.Erp/Pages/Catalog/Categories/Index.cshtml.cs`, `Leitor.Erp/Services/Sales/ProductCategoryAppService.cs`, `Leitor.Erp/Entities/ServiceCatalog/ServiceCatalogItem.cs`.
**Original hypothesis was wrong**: `ProductCategoryAppService.GetListAsync` has no filter predicate at all beyond the plain `CrudAppService` base (no product/service scope, no tenant flag) — and `Catalog/Create.cshtml.cs`'s product-category dropdown queries the exact same `ProductCategoryAppService.GetListAsync`, so the index page and the create-a-product dropdown are provably reading identical data. No scoping bug exists there.
**Real bug found**: `Product.CategoryId` is a proper `Guid?` FK into `ProductCategory` — but `ServiceCatalogItem.Category` (line 14) is a **free-text `string?`**, entirely disconnected from `ProductCategory`. This *is* the "enum/string mirrors catalogue by name, no FK" pattern from `project_cybersecurity_service_reframe_2026-08-18`, just in a different spot than first guessed. Anyone categorizing entries in the Service Catalog types a category name with no dropdown and no reuse — nothing ties it to `ProductCategory`, so (a) it never shows up under Catalog & Inventory → Categories (wrong table), and (b) free-typed names drift with no consolidation ("Networking" vs "Network" vs "networking"), which plausibly is what "Duplicate data" was pointing at.
**Fix (not done):** convert `ServiceCatalogItem.Category` from a free-text string to `Guid? CategoryId` referencing `ProductCategory` (or a renamed shared category table if product/service categories should stay visually distinct but share the same underlying list), plus a data migration for existing free-text values (best-effort match-by-name into new/existing `ProductCategory` rows). This is a real EF Core migration + data-migration task, not a quick fix — **deliberately not started this pass**: another concurrent process was actively modifying `Leitor.Erp/Data/ErpDbContext.cs` for item 4's work while this was being investigated, and generating a second migration against the same DbContext version concurrently is a real collision risk. Pick this up once that lands, and check migration history first.

### 6. [ ] Identity/HR overlap; generalize Cybersecurity into an assessment-template engine
- **a.** Employees *are* system users — Identity Management (Roles/Users) and HR (Employees) shouldn't be two disconnected trees; role/job-description management belongs as an extension of HR. This is the identity-fragmentation problem already documented and only partially fixed per `project_identity_model_audit_2026-08-18` — route through that audit's recommendation rather than redesigning fresh.
- **b.** Cybersecurity should stop being a standalone module wrapping one narrow `SecurityAssessment` entity (`Leitor.Erp/Entities/Cybersecurity/SecurityAssessment*.cs`, `Pages/Cybersecurity/Assessments/*`). Instead: a generic assessment-template/checklist engine where the user picks a category from a dropdown (Cybersecurity, CCTV, Network, Digital Marketing, etc.), each backed by its own best-practice checklist; a customer can have multiple assessments across categories; a completed assessment drives a Proposal. This is exactly the design already scoped in `project_checklist_engine_design_2026-08-18` (generic Template/Section/Item → Instance/InstanceItem, built from ContractTemplate/ProjectTask/Proposal precedents) — implement that design, retiring `SecurityAssessment*` in favor of a seeded "Cybersecurity Assessment" template.
